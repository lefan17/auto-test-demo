# 质量门禁策略

这份文档回答一个问题：**哪一层测试在什么时候跑、红了到底拦不拦、多久算超预算。**
在此之前，这套策略只活在 `.github/workflows/test.yml` 的 `continue-on-error` 行里——
它事实上一直在生效，但没人能靠读文档说清「UI 到底阻不阻塞」，于是每一次讨论都要重新翻 YAML。

现在这里写的每一句都可以被机器验：`python scripts/check_gate_policy.py` 会读
`pytest.ini` 的 marker、`.github/workflows/test.yml` 的 job 与放行步骤、以及本文档的三段
机器可读表格，逐条对照。**改了 workflow 不改文档，或者改了文档不改 workflow，这个脚本都会红。**
所以本文档不是说明文，是门禁的一部分。

## 一、触发时机

`.github/workflows/test.yml` 第 4-19 行声明了四个触发源，它们是本文档里所有层共享的调度：

| 触发源 | 条件 | 谁在等它 |
|---|---|---|
| `pull_request` | 目标分支 `main` | 作者本人，等绿灯才能合并 |
| `push` | 分支 `main` | 全员，`main` 必须随时可发布 |
| `schedule` | `cron: "0 18 * * 1"`（UTC 周一 18:00 ＝ 北京时间周二 02:00） | 无人阻塞等待，产出用于发现「没人改代码但环境变了」的漂移 |
| `workflow_dispatch` | 手动点按钮 | 排障与复现 |

并发控制在第 26-28 行：`cancel-in-progress` 只在 `pull_request` 上开启。理由很直接——
PR 上的旧提交已经作废，取消能省机器；而 `main` 上的每一次 push 都是发布记录，
被后一次 push 顶掉就等于「这段代码从没被验证过」，所以必须跑完。

**除 `perf` 外的六个 job 在四个触发源下全部执行，没有任何 job 是「只在夜间跑」的。**
这不是疏漏：本仓库的夜间回归价值在于**用同一套用例在无人改动代码时再跑一遍**，
而不是跑一套白天不跑的用例。真正按层区分的调度写在下面第三节的 marker 表里。

唯一的例外是 `perf`（第 722 行）：它带 `if: github.event_name == 'workflow_dispatch' || github.event_name == 'schedule'`，
**只在手动与周一夜间跑，PR 与 push main 都不触发**。理由它自己的注释写了：一批 4 梯度 × 2 次 × 20s 要
约 200 秒，而且数字天然带 10% 量级的批次间噪声——拿它当 PR 门禁等于给每个 PR 加一个随机红灯，
最后一定被人豁免或删掉。它也是**唯一一个 job 级 `continue-on-error`**（见第四节），
所以它即使红了也不会让流水线变红：结论要人读 artifact 自己判断。

「阻塞」的判据是客观的：这个 job 里**没有任何** `continue-on-error: true` 的步骤，
于是它一旦非零退出，整条流水线红，PR 合不进去。
`test` 标「部分放行」而不是「不阻塞」，因为它里面七组判定步骤全都不设豁免，只有 UI 那一步例外。

失败找谁一栏对七个 job 是同一个答案，这不是偷懒：`CODEOWNERS` 第 18 行是 `* @lefan17`，
`testcases/`、`scripts/`、`.github/`、`requirements*.txt`、`pyproject.toml` 也全部指向同一人——
**单人仓库里「找谁」不需要按路径分流**。等有了第二个 owner，这一栏才需要按路径细分成多行。

失败不是只挂红灯：第 524-546 行的「失败自动开 issue」step 在
`if: failure() && (github.event_name == 'schedule' || github.event_name == 'push')` 下开一条
label 为 `ci-failure` 的 issue。**只在夜间与 push main 上开**，是因为 PR 上的红由作者自己看着改，
再开 issue 只会制造噪音；而夜间与 `main` 上的红没有具体的人在现场，必须落到那里才有人看见。

## 三、marker 表

`pytest.ini` 声明了 12 个 marker。它们不是十二个并列的测试层，而是**四种东西**：
`api` / `ui` / `mes` / `login` / `contract` / `perf` / `platform` 是**宿主层**（按被测对象切开，各自对应 CI 上的一次 pytest 调用）；
`smoke` / `regression` 是**横切风险标签**（表示「这条用例值得在什么时机被优先关注」，不单独成层）；
`flaky` / `quarantine` 是**质量治理标签**（不表示层级，表示这条用例当前的稳定性处置）；
`covers` 是**归属声明标签**（声明「这条用例覆盖哪个 operationId」，供 qaplat registry 构建覆盖矩阵，
它既不是层也不是处置，当前 0 条用例挂它）。表里逐条写明归属。

表里的条数是 `pytest --collect-only -q -m <marker> -o addopts=` 的实测收集数，
不是手写的估计值——它随各波新增用例而变，**读这张表时应以命令重跑一次为准**，
本节末尾给了复核命令。`perf` 同时挂了 `api` 标记，所以它的条数会体现在 `api` 那一行里。

**批次 2（`traffic-replay/`）不在这张表里，因为它根本不是根仓库的一层。**
它是一个自成一体的子项目：自带 `pytest.ini`（`testpaths = tests`、`addopts = -v -ra --strict-markers`）
与自己的 `conftest.py`，marker 是 `recorder` / `replay` / `analyze`——与根这 12 个 marker **零重叠**，
两边的名字没有任何一个相交，所以「谁的用例归谁的门禁」不需要靠标签去辨别。
CI 上它由 `test` job 里一个 `working-directory: traffic-replay` 的独立 step 跑（173 条，失败即阻塞），
根 pytest 的 `testpaths = testcases` 收不到它，根那 12 个 marker 也没变。
也正因为零重叠，`scripts/check_gate_policy.py` 不需要为它登记 marker：那个脚本只读**根** `pytest.ini`
的 markers 块，子项目的 marker 从不在它的真值来源里。

**为什么 `smoke` / `regression` / `perf` / `flaky` 不单独开一个 CI step。**
实测这四个标签的用例集合是宿主层的子集：`smoke` 36 条、`regression` 93 条、
`perf` 2 条、`flaky` 33 条，全部落在 `api` / `mes` / `ui` 三个宿主层里（子集探测结果：outside = 0）。
再给它们各开一次 pytest 调用，等于把同一批用例跑第二遍，只买到更长的流水线。
所以它们的作用是**给人和给脚本用的选择器**——本地开发用 `pytest -m smoke` 拿到几十秒的快速反馈，
发版前用 `pytest -m regression` 确认高风险面，CI 上用宿主层一次跑全。
本地命令在 `README.md` 的运行命令表与 `CONTRIBUTING.md` 里。

`perf` 有一处**必须手动跑**的理由：它采样的是 p95 这类性能数字，只有独占机器时才干净，
混在 `-n 4` 的并行组里采出来的数会被同机其它 worker 干扰。所以 `pytest -m perf` 是
给「要看基线准不准」的人用的，日常由 `-m api` 顺带跑到（顺带跑的那次只当冒烟）。
重采基线用 `UPDATE_PERF_BASELINE=1 pytest -m perf`，理由见 `docs/wave3-load-handoff.md`。

宿主层之外有两类被测对象，因此有两个**必须独立成 step** 的例外：

1. `contract`：224 条**完全落在宿主层之外**（它是独立的第四类被测对象——
   OpenAPI 文档与实现的漂移），因此它必须有自己的 step，也就是第 241-244 行那一步。
2. `platform`：105 条**完全落在宿主层之外**（被测对象是**平台自己**——qaplat 的 registry 覆盖矩阵、
   metrics_store 落盘格式、gate_layers 门禁分层、drift_report 报表 CLI）。判定依据是
   `-m "platform and (api or ui or mes or login or contract or perf)"` 收集数 = 0，
   即 `-m api` / `-m mes` / `-m login` 三步一条都跑不到它。它必须有自己的 step，
   也就是第 353-354 行那一步。**改前这条事实是：`.github/workflows/test.yml` 全文没有出现过
   `platform` 字样**——那 105 条在 CI 上永远不会被执行，平台层会静默腐烂，
   而门禁脚本 `scripts/check_gate_policy.py` 自己就住在由平台层判定的分层体系里。

**覆盖率门禁挂在 `-m api` 那一步（第 246-260 行），阈值 40%。**
理由写在 workflow 第 262-274 行：门禁要拦的是「这一组用例还测不测得住」，
挂在 `-m api` 上时覆盖率数据与「跑的是哪批用例」是同一份，不需要为凑数再跑一遍契约；
取 40 而不是当前实测值（本组 78.87%，全量 `-m "not ui"` 88.90%），是留出余量——
**门禁拦「退化」，不锁死「当前值」**，否则每次重构都要顺带改阈值，阈值一改就再也没人信它。

## 四、放行清单（`continue-on-error`）

全 workflow 只有三处 `continue-on-error`（两处 step 级、一处 job 级），都在这里逐条登记。
这张表是脚本的强校验项：workflow 里新出现一处豁免而没登记在这里，脚本直接红。
job 级豁免不属于任何一步，步骤名就写 `<job 级>`——它是整条 job 的豁免，语义比 step 级更强，
**只能**对应「不阻塞」；step 级豁免则对应「部分放行」或「不阻塞」。

<!-- gate-policy:continue-on-error -->
| job | 步骤 | continue-on-error | 为什么放行 |
|---|---|---|---|
| `test` | `运行 UI 自动化（失败不阻断流水线）` | true | UI 打公网第三方站点，失败可能来自站点改版/网络/浏览器，不能代表这份代码坏了；理由、风险与退出条件见第六节 |
| `security` | `pip-audit（扫描锁定的依赖树）` | true | 它查的是**公共漏洞库的当前状态**，不是这份代码的质量；设成阻塞等于让「上游今天披露了一个 CVE」变成「任何人的 PR 今天都过不去」，结果一定是有人把它删掉 |
| `perf` | `<job 级>` | true | 容量压测的数字天然带 10% 量级的批次间噪声，红了不能说明代码坏了；而且它本来就只在手动/夜间跑，用 job 级豁免让它连流水线结论都不影响，结论由人读 `perf-results` artifact 判断 |
<!-- /gate-policy:continue-on-error -->

**这三处豁免都不是「不管了」。** UI 那一步照样产出 Allure 报告与失败截图
（第 419-449 行），`security` 的红照样出现在 job 日志与流水线摘要里。
区别只在于：它们不获得把整条流水线弄红的权力。

**加严是单向的。** 本仓库不允许把任何现有 job 从阻塞改成非阻塞——
这类改动的收益是「今天我不用处理这个红」，代价是把一个真问题永久性地变成静默失效。
要新增检查，就新增 job；要放宽已有的，必须先改本文档的第二、四节，并在 PR 描述里写清退出条件，
而脚本会红着提醒你这件事正在发生。

## 五、flaky 与 quarantine 的处置策略

### 5.1 `flaky`：重跑只对「第三方抖动」指纹生效

现状（实测）：`testcases/api/flaky_policy.py:45` 定义了
`NETWORK_FLAKY = pytest.mark.flaky(reruns=1, only_rerun=NETWORK_JITTER_PATTERNS)`，
其中 `NETWORK_JITTER_PATTERNS`（第 22-37 行）是 **6 条**指纹正则：
`实际状态码: (?:429|5\d\d)`、`Max retries exceeded`、`ConnectionError`、`Timeout`、
`响应不是合法 JSON`、`接口响应过慢`。它挂在 `api` 层的 33 条公网用例上
（`test_post.py:10`、`test_response_time.py:8`、`test_user_create.py:9`、`test_user_list.py:7`）。

**三条边界，缺一条这套机制就变成洗红工具：**

1. **`addopts` 里没有 `--reruns`。** `pytest.ini:11` 是 `-v -raR --strict-markers`，那个 `R` 只是
   让 pytest-rerunfailures 的重跑段落被打印出来。全局 `--reruns` 会把真回归一起吞掉——
   「失败了但重跑过了」在报告里就是一个绿灯，没人会去翻。
2. **指纹只收第三方抖动。** 字段不匹配、Schema 校验失败、类型错误、存在重复这些
   **契约型**失败被刻意排除在指纹之外（`flaky_policy.py:39-41`）。匹配对象是
   `f"{type(exc).__name__}: {exc}"`；不匹配指纹时 pytest-rerunfailures 走
   `_should_hard_fail_on_error`，**当场硬失败，一次都不重跑**。
3. **重跑必须留痕。** 根 `conftest.py` 的 `pytest_runtest_logreport`（第 154-162 行）把重跑次数
   与最终结果写进 `reports/flaky-governance.json`，CI 上第 388-390 行用
   `scripts/flaky_report.py --markdown` 无条件（`if: always()`）把它们打进流水线摘要，
   同时上传为 `flaky-governance` artifact。**「这次是重跑才过的」必须天天可见**，
   否则重跑就从「吸收抖动」变成「隐藏抖动」。

维护方式：`flaky` 不是靠手打 `@pytest.mark.flaky` 用的（实测全仓没有一处裸用法），
统一通过 `NETWORK_FLAKY` 别名挂载。**新增公网用例请挂这个别名，不要自己写 `pytest.mark.flaky`**——
裸标记会拿到插件默认的 `reruns=1` 而**没有** `only_rerun` 收窄，等于对任何失败都重跑。

### 5.2 `quarantine`：退出门禁，但必须点名

现状（实测）：`pytest.ini:26-29` 声明了 `quarantine`。根 `conftest.py` 的行为是：

- `pytest_collection_modifyitems`（第 126-144 行）：**非** quarantine 运行里，把带
  `quarantine` 标记的用例从收集中移除，并调用标准钩子 `pytest_deselected`，
  让它们计入 pytest 的 "N deselected" 计数。**这不是判为通过**——它们既没通过也没失败，
  只是不计入本次门禁。
- `pytest_terminal_summary`（第 201-213 行）：在终端摘要里逐条打印清单：
  `==== quarantine：N 条用例已退出主门禁 ====`、每条 `  DESELECTED <nodeid>`、
  以及「这些用例既没有被删除，也没有被判为通过——它们的红不再计入本次门禁。」、
  `单独运行：pytest -m quarantine`、账本路径。
- 同一份清单写进 `reports/flaky-governance.json` 的 `quarantined` / `quarantined_count` 字段
  （`conftest.py:165-186`），CI 上由 `flaky_report.py --markdown` 打进流水线摘要。

**策略三条：**

1. 进隔离区必须附带一条「谁在什么时候之前处理」的记录，落在 `docs/wave2-flaky-handoff.md`
   或对应的 issue 里。隔离区是**延期**，不是**赦免**——没有归期的隔离用例就是被删掉的用例，
   只是没人承认。
2. **主门禁里清单必须可见。** 这条已经实现并被元测试锁住：
   `testcases/api/test_flaky_governance_meta.py:123` 断言
   `f"DESELECTED {QUARANTINE_PROBE}::test_probe_quarantined_known_failure" in proc.stdout`。
   谁把这条打印去掉，元测试红。
3. **不为 quarantine 单独开 CI step**（workflow 第 404-407 行的注释是这么定的）：
   隔离区当前 0 条，`pytest -m quarantine` 空跑返回 exit=5，GitHub Actions 会把它当失败——
   于是「一件好事」会天天把流水线弄红。隔离清单由 `flaky_report.py --markdown`
   无条件打印，信息不会丢。**当隔离区长期非空时这条要重新评估**：那时它就不再是空跑，
   而是每天都该有人看见的一组已知红。

## 六、UI 不阻塞：理由、风险与退出条件

这是本仓库唯一一处「用自己的测试逻辑换稳定性」的妥协，所以它必须被论证，而不是被习惯。

### 6.1 为什么现在不阻塞

1. **失败归因不可靠。** UI 用例打的是公网 `https://www.saucedemo.com`（`data/config.yaml`）。
   一次失败可能来自我们的选择器过期、站点改版、跨境网络抖动、浏览器版本漂移。
   **一个无法在失败瞬间区分「谁的错」的信号，不该拥有阻塞权**——
   阻塞权的前提是「红灯＝这段代码坏了」，而这个前提在公网 UI 上不成立。
2. **它没有可复现环境。** `api` / `mes` / `login` / `contract` 四层要么打可控的 demo 接口、
   要么 fixture 自起本地服务，红灯可以本地复现。UI 不能。
3. **耗时与不稳定互相放大。** 第 294-296 行记录：UI 刻意不开 `-n` 并行，
   因为只有 2 个测试文件、`-n 4` 只用上 2 个 worker，启动开销大于收益；
   而浏览器并发会显著抬升公共 demo 站的失败率。给一个「越并行越不稳」的层配阻塞权，
   换来的是「PR 排队等一个看天吃饭的 job」。

### 6.2 风险（说清了才叫权衡，说不清就是放任）

1. **静默腐烂**：`continue-on-error` 最危险的后果不是「这次红了没人管」，
   而是「它已经红了三个月没人知道」。UI 用例的失效是渐进的——站点改一次 DOM，
   三个选择器失效，红灯被豁免吞掉，下一个 PR 照样合。
2. **覆盖停止生长**：没有红灯压力，就没人愿意往 UI 层加用例。UI 是**唯一**验证
   「用户可见行为」的层，它萎缩到 34 条之后，`api` + `mes` 全绿也不代表用户能登录。
3. **报告靠自觉**：Allure 报告、失败截图（`ui-screenshots` artifact，第 442-449 行）、
   流水线摘要都在产出，但**没有任何机制强制人打开**。这些产出的价值取决于是否有人看。

**当前的缓解措施**（都是既有事实，不是承诺）：UI 进入夜间回归（四个触发源全覆盖），
失败截图与 Allure 报告照样上传，摘要里 UI 那一行明确写着「（失败不阻断）」。

### 6.3 退出条件：什么情况下应该改成阻塞

满足以下任一条，就应该把 `test.yml:299` 的 `continue-on-error` 删掉，并把本文档第二节
`test` 的阻塞性改成「阻塞」、第四节删掉对应行（脚本会红着提醒这几处必须同时改）：

- **A. 外部依赖消失**：UI 用例不再打公网站点——改为 fixture 自起本地站点
  （或把页面路由全部 mock 掉），失败可在本地复现。**这一条一满足就立即改**，
  因为它直接消掉了 6.1 的第 1、2 条理由。
- **B. 稳定性有数据**：最近 **20 次** CI 运行的 UI step 中，「非代码原因」的失败 ≤ 1 次
  （成功率 ≥ 95%），且每次失败都能凭截图/Allure 明确归因到站点或网络而非我们的脚本。
  这条要求**先积累数据**，这也意味着现在就该开始统计——`reports/flaky-governance.json`
  已经是现成的落点。
- **C. 站点改版与脚本陈旧被解耦**：引入页面对象契约（例如对关键页面结构做快照断言），
  让「站点改版」表现为一条**确定的**契约失败而不是随机的选择器超时。
  这样红灯重新变得可归因，6.1 的前提就不再成立。

### 6.4 改成阻塞时要一起改的地方（脚本会拦）

1. `.github/workflows/test.yml` 第 299 行：删掉 `continue-on-error: true`。
2. 本文档第二节 `test` 的阻塞性、第四节放行清单。
3. `README.md` 第 785-793 行的 job 表（`test` 行的「UI 那一步除外」）与第 804-809 行的措辞。
4. `CONTRIBUTING.md` 里「CI 必须全绿才能合并」那一段。
5. `CHANGELOG.md` 的未发布段。

## 七、预算时长

「预算」＝ job 的 `timeout-minutes`，是硬上限：超时即判失败。
它也不是拍出来的，而是给实测值的余量，防止一次网络卡顿把「慢」变成「红」。

| job | 预算 | 实测参照 |
|---|---|---|
| `lint` | 10 分钟 | 本机 `ruff check .` 0.25s + `ruff format --check .` 0.20s |
| `typecheck` | 15 分钟 | 单文件 mypy 秒级；全量随缓存波动 |
| `test` | 45 分钟 | 接口组本机 `-n 4 --dist loadfile` 30.4s；业务全链路 27.1s；契约 23.3s；登录契约 2.6s；qaplat 平台层 8.2s；流量回放子项目 15.4s（批次 2，自带 pytest.ini 的 173 条）；UI 30.8s（均在本机实测，CI 上更慢但远低于预算） |
| `security` | 15 分钟 | `pip-audit` 联网查漏洞库 |
| `pre-commit` | 15 分钟 | 全仓 ruff + 各类文件校验 |
| `commit-convention` | 10 分钟 | 纯文本校验，秒级 |
| `perf` | 20 分钟 | 4 梯度 × 2 次 × 20s 的压测本体约 200 秒，另加起服务与依赖安装（`requirements-perf.txt` 里的 locust）；见 `docs/wave3-load-handoff.md` |

分层预算的意义在于**让「慢」先于「红」被看见**：`test` 拿到 45 分钟而不是 15 分钟，
是因为它装了六个层；如果哪天 `test` 逼近 45 分钟，正确动作是拆 job 而不是抬预算——
抬预算会把「某个层变慢了」这件事变成不可见。

## 八、怎么用、怎么改

```bash
python scripts/check_gate_policy.py        # 对照表；不一致退出 1
python scripts/check_gate_policy.py -v     # 逐条打印 job 与 marker 的归属行号
```

脚本读三处真值：`pytest.ini` 的 `markers` 块、`.github/workflows/test.yml` 的 job /
`timeout-minutes` / `continue-on-error`、以及本文档三段
`<!-- gate-policy:... -->` 注释之间的表格。它**不解析**人写的散文与注释，只看结构化事实——
所以「换个说法」不会让它误判，但「文档说阻塞、workflow 已经豁免」一定会。

改动流程：

1. 动 `test.yml` 的 job 集合、`timeout-minutes`、`continue-on-error`，或动 `pytest.ini` 的 marker，
   **同一个 PR 里**改本文档对应表格。
2. 跑 `scripts/check_gate_policy.py`，绿了再提交。CI 上这一步已经接进 `pre-commit` job
   （`test.yml` 里 `pre-commit run --all-files` 之后的那一步），属于**只加严**的新增检查——
   它不豁免任何已有的门禁，只多拦一种错。
3. 只在文档里改措辞、不动三张表的，脚本不受影响。
