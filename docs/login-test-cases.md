# 登录接口测试用例设计（30 条）

> 被测接口：`POST /api/login`（实现见 `login_app/app.py`，契约见 `docs/login-contract.md`）
> 配套自动化用例：`testcases/login/test_login_contract.py`（LC-01 ~ LC-30，落地 29 条）
> 运行：`pytest -m login`

## 这份文档和用例的关系

**文档负责"设计"，用例负责"执行"。** 30 条用例是用 5 种设计方法推出来的，
用例文件里每条都标了对应编号 —— 这样做的意义是：当有人问"你怎么保证测全了"，
你能拿出**方法**和**映射关系**，而不是一句"我凭经验想的"。

## 接口契约

| 项 | 内容 |
|---|---|
| 请求方法 | POST |
| 请求体 | JSON：`username`(string, 必填)、`password`(string, 必填) |
| 200 | 登录成功，返回 `token` 与 `user` |
| 400 | 缺少用户名或密码 |
| 401 | 用户名或密码错误 |

> **契约的边界**：上面这张表只定义了 200/400/401 三种结果。
> 实现实际还会返回 405（方法不对）和 422/500（框架层），这些**没写进契约**。
> 契约没写但实现会返回的状态码，本身就是一类风险 —— 见用例文件末尾的
> `test_undocumented_status_codes_are_still_undocumented`。

## 设计方法速览

| 方法 | 一句话解释 | 本用例覆盖 |
|---|---|---|
| 等价类划分 | 把输入分为"有效/无效"类别，每类取代表值 | LC-01~LC-13 |
| 边界值分析 | 测边界上/内/外的值 | LC-15~LC-21 |
| 判定表 | 多条件组合，保证覆盖所有分支 | LC-22~LC-25 |
| 场景法 | 按业务流程/协议层走 | LC-26~LC-29 |
| 错误推测 | 凭经验猜"容易出错的地方" | LC-20/21/30 |

> **为什么等价类和边界值要一起用**：等价类告诉你"每类取一个代表"，
> 但它管不住边界 —— 密码 `123456` 和 `1234567` 属于同一个等价类（都错），
> 可它们是不同的边界。**只做等价类会漏掉边界，只做边界值覆盖不了类别**，
> 两个方法是一对，不是二选一。

| LC-20 | 错误推测 | 用户名含 HTML 脚本 | <script>alert(1)</script> / 123456 | 200 且原样回显（前端需转义，防 XSS）**FIND-05** | P1 |

| LC-22 | 判定表 | 有用户+有密码+密码对 | admin / 123456 | 200 | P0 |
| LC-23 | 判定表 | 有用户+有密码+密码错 | admin / bad | 401 | P0 |
| LC-24 | 判定表 | 无用户+有密码 | {"password":"123456"} | 400 | P0 |
| LC-25 | 判定表 | 有用户+无密码 | {"username":"admin"} | 400 | P0 |
| LC-26 | 场景法 | token 为非空字符串 | admin / 123456 | token 是字符串且非空 | P1 |

| LC-28 | 场景法 | GET 访问登录接口 | GET /api/login | 405 | P1 |
| LC-29 | 场景法 | 非 JSON 文本请求体 | "not-json" (text/plain) | 400 | P1 |
| LC-30 | 错误推测 | 多余字段 | admin/123456 + role:admin | 200（宽松处理，忽略多余字段） | P2 |

> **LC-21 的措辞值得注意**：预期写的是"无注入漏洞，但暴露无用户校验"。
> 严格说，这条用例**没有**证明服务端防注入 —— 它压根不查数据库，
> 注入根本没有发挥的余地。把"没测出问题"当成"没有问题"是测试里最危险的
> 自我安慰之一，这里在文档和用例注释里都写明它证明了什么、没证明什么。

## 测试发现点（值得写进缺陷清单/报告的内容）

| 编号 | 级别 | 发现点 | 对应用例 |
|---|---|---|---|
| FIND-01 | 中 | **无用户存在性校验**：任意用户名 + 正确密码 123456 都能登录成功 | LC-02 |
| FIND-02 | 低 | **契约偏差（宽松）**：实现额外接受表单提交，契约只定义了 application/json | LC-05 |
| FIND-03 | 低 | **username/password 处理不对称**：用户名 trim，密码不 trim | LC-03 / LC-17 |
| FIND-04 | 低 | **无长度限制**：超长用户名/密码均可提交 | LC-18 |
| FIND-05 | 中 | **用户名原样回显**：若前端未转义存在 XSS 风险 | LC-20 |
| FIND-06 | 中 | **token 为固定值**：无签发时间、无过期，仅适合演示 | LC-27 |

> FIND-01 和 FIND-06 合起来才是完整的问题：**没有用户校验 + token 永久固定**，
> 等于任何人都能用任意身份进来，且进来之后凭证不会失效。
> 单独看每一条都像"小毛病"，合起来是一句话：**这套登录不能上生产**。

## 缺陷清单与用例的分工

发现点写在这里（文档），用例里则**断言当前行为**（`assert r.status_code == 200`，
并注明 `FIND-0x`）。为什么不把用例写成"期望它被修好"（`assert == 400`）？

因为那样用例会常年红着，团队很快学会"这几条是已知失败，忽略即可"，
然后**真的失败也没人看了**。写成钉住当前行为的形式，用例是绿的，
但一旦有人修好了、或者改坏了，它立刻报警。缺陷本身由缺陷清单跟踪，
用例负责当"行为变化探测器"。

这个分工在真实项目里很常见，面试也常问 —— 值得能讲清楚。
