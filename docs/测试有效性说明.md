# 测试有效性说明：这些用例到底验证了什么

> 本文回答一个比"用例全绿"重要得多的问题：**把被测代码改坏，用例会红吗？**
> 用例全绿本身不构成任何证据 —— 一条什么都没断言的用例也是绿的。
> 所以下面每一条都按同一个格式写：**变异（把代码改坏）→ 改前结果 → 改后结果**。
> 所有变异都在项目副本里做，做完即弃，主仓库只留修复。

## 判定方法：变异实验

对每条承重断言，构造一个"把这条断言本该看守的行为破坏掉"的最小改动，
然后跑 `pytest -m mes`，看用例是否变红：

- **变异后变红** = 这条断言真的在承重（有效）；
- **变异后照样全绿** = 假绿：断言不存在、或断的东西和它声称防的事故无关。

修前的完整变异记录（29 条 MES 用例）：

```text
MUTATION=none (基线)                         29 passed
MUTATION=race 整体换成纯串行 for 循环          29 passed   ← 假绿
MUTATION=幂等释放逻辑整个禁用（if False）      29 passed   ← 假绿
MUTATION=写流水时 balance 多记 1             29 passed   ← 假绿
```

三条"承重断言站不住"全部复现。下面逐条说明为什么没被检出、现在靠什么检出。

## 1. 并发用例的承重结构可以被整体替换

**改动文件**：`testcases/mes/conftest.py:138-182`（`race` fixture）、
新增 `testcases/mes/concurrency.py`、`testcases/mes/test_mes_business.py:267-281`、`:338`。

**变异方式**：把 `conftest.py` 的 `race` fixture 整个替换成"普通 for 循环顺序调用"，
即删掉 `threading.Barrier` 与多线程，让两个请求一前一后跑完。

**为什么没被检出**：`race` fixture 的 docstring 写得完全正确 ——
"不能简单地起 N 个线程然后 join……这样根本构不成竞态，用例会稳定通过，但什么都没验证到"。
问题是**这句话只写在注释里**：`race` 自己不做任何并发自检，
用例拿到的是 `(results, elapsed_ms)` 二元组，对"请求是否真的同时跑过"零断言。
于是"并发"这件事的全部约束力都寄托在 fixture 的实现上 ——
而 fixture 是可以被整体替换的，替换之后注释还在、用例还绿。

**现在靠什么检出**：
1. `race` 改为返回 `(结果列表, 墙钟毫秒, 每个请求的起止时间)` 三件套，
   在 `wrapper` 里用 `time.perf_counter()` 记下每个请求的 `(开始, 结束)`（`conftest.py:162-167`、
   `return results, elapsed_ms, spans` 在 `:180`）。
2. 判定口径放在**独立模块** `testcases/mes/concurrency.py`：
   - `race_timeline(outcome, workers=2)`（`concurrency.py:36-53`）先校验返回值形状，少一段时间线就直接红；
   - `assert_requests_overlapped(...)`（`concurrency.py:56-75`）断言**至少两个请求的时间区间真的交叠过**（`overlap_ms > 0`），失败时打印每段 `+xms → +yms` 的完整时间线。
3. 断言写在**用例正文**：`test_concurrent_approve_only_one_wins`
   （`test_mes_business.py:280-281`）与 `test_concurrent_issue_never_oversells`（`:329`、`:338`）
   都先验"真的并发过"，再看业务结论。口径放在 fixture 里会被变异一起抹掉，放正文里抹不掉。

**为什么判据是"区间交叠"而不是"总耗时更短"**：后端用 `BEGIN IMMEDIATE` 把写请求串行化
（`mock_server/db.py` 的 `write_tx`），并发请求会排队，**并发跑反而比串行慢**。
实测同一对审核请求：并发墙钟 25.4ms / 串行 4.8ms；领料（有 300ms 并发窗口）并发墙钟 745ms / 串行 608ms。
拿耗时当判据会得出完全错误的结论，能区分"并发"与"排队"的只有时间线本身
（实测并发交叠 3.4~403.7ms，串行交叠恒为 -0.0ms）。

**变异后结果**（`pytest -m mes`）：

```text
MUTATION=race 换成串行、沿用旧的二元组返回：
  AssertionError: race 必须返回 (结果列表, 墙钟毫秒, 每个请求的起止时间) 三件套；
  实际拿到 tuple，长度 2。少了时间线，"这些请求真的同时跑过"就无法被验证 —— 并发用例会退化成假绿。
  testcases\mes\concurrency.py:42
  2 failed, 28 passed, 76 deselected, 1 error in 6.92s   EXIT=1
  FAILED ...TestOptimisticLock::test_concurrent_approve_only_one_wins
  FAILED ...TestConcurrentInventory::test_concurrent_issue_never_oversells

MUTATION=race 换成串行、但返回三元组（更隐蔽的变异，形状对不上就骗不过去）：
  AssertionError: 并发审核同一张工单：2 个请求的时间区间没有任何交叠（最长交叠 -0.0ms），
  说明它们其实是**排队串行**跑完的，这条用例根本没验证到并发行为。
  testcases\mes\concurrency.py:70
  2 failed, 28 passed, 76 deselected in 6.86s   EXIT=1
```

> 附带发现（顺手修的时序缺陷）：改前 `test_concurrent_issue_never_oversells` 是在
> 断言成功次数**之后**才记录"该退多少料"，一旦断言先红，退料量就没算出来 ⇒
> 领走的料永远退不回去，脏数据顺着会话级隔离检查传染给整场会话。
> 已把"算 ok_count、登记退料量"提到所有断言之前（`test_mes_business.py:333-336`），
> 所以**只要 race 还交回结果**，用例失败也能收尾。
>
> 上面第一条变异输出里仍有一个 `1 error`：那个变异把 `race` 换成了返回**二元组**的
> 串行实现，`race_timeline` 的形状校验（`concurrency.py:42`）在 `ok_count` 算出来之前
> 就抛了 —— 这种情况下确实没法知道该退多少料。这个 `error` 是
> `data_isolation_check` 报出来的，内容是
> `库存可用量合计: 基线 3270.000 -> 现在 3211.999（差 -58.001）`，
> 也就是说**会话级隔离检查自己把泄漏抓住了**，同样是红、同样指向真正的问题，
> 不是误报。第二种变异（返回三元组的串行实现）因为形状对得上，
> 走完了登记退料的代码，就没有这个 error（`2 failed, 28 passed`，无 error）。

## 2. 并发领料的"被拒分支"从未执行

**改动文件**：`testcases/mes/test_mes_business.py:297-369`。

**变异方式 A**：把后端库存守卫去掉（`mock_server/services.py` 里
`if row["available_milli"] < qty:` 改成 `if False and ...`），模拟"扣成负数也不拦"。
**变异方式 B**：把 `write_tx` 的 `BEGIN IMMEDIATE` 改成 `BEGIN`（DEFERRED），
让两个并发请求都读到同一份旧库存。

**为什么没被检出**：种子库存 `MAT-CU-001 / WH-01 = 120.000`（`mock_server/db.py:188`），
而用例单次只领 `30.000` —— **两个请求都成功**，写了
"必须被拒且返回 400 INSUFFICIENT_STOCK"的那段断言（改前 `:284-287`）**一次都没执行过**。
更根本的是"不超卖"这条不变量在串行（`BEGIN IMMEDIATE` 排队）下同样成立：
两个请求一前一后各扣 30，账实照样相符，所以把事务隔离降级也看不出问题。

**现在靠什么检出**：
1. 单次领料量按**实测库存**算出来，而不是写死：
   `per_milli = before_available // 2 + 1`（`test_mes_business.py:324`）⇒
   两个请求不可能都成功，**"被拒分支"每次都会真的执行**；同时第一个请求必然扣得动。
   种子的可用量以后被改动，用例也不会悄悄退化回"两次都成功"。
2. 断言 `ok_count == 1`（`:340-345`）——成功两次即判超卖，并把响应码与耗时打进失败信息。
3. 被拒的那次必须是明确的业务结论：`resp.status_code == 400` 且
   `mes.error_code(resp) == "INSUFFICIENT_STOCK"`（`:347-351`），不是 500、不是别的码。
4. 保留并收紧守恒不变量：`issued` 增量 == 单次量 × 成功次数（`:355`）、
   `available` 减量与之相等（`:360`）、`available >= 0`（`:363`）、流水条数 >= 成功次数（`:366-369`）。
   这几条在"恰好成功 1 次"下依然成立，且是"不超卖"真正的内容。

**变异后结果**：

```text
MUTATION=库存守卫去掉（if False）：
  apis.mes_api.ApiError: 期望 HTTP 400，实际 500
  {"code":"INTERNAL_ERROR","detail":{"exception":"IntegrityError"}}
  FAILED ...test_concurrent_issue_never_oversells
  FAILED ...test_issue_beyond_stock_is_rejected_and_stock_unchanged
  2 failed, 28 passed, 76 deselected in 6.80s   EXIT=1
  （库存表的 CHECK (available_milli >= 0) 兜住了数据，接口层变成 500 —— 用例报了红。）

MUTATION=BEGIN IMMEDIATE -> BEGIN（DEFERRED）：
  AssertionError: 并发领料被拒时状态码异常: 500 {"code":"INTERNAL_ERROR","detail":{"exception":"OperationalError"}}
  testcases\mes\test_mes_business.py:350
  1 failed, 29 passed, 76 deselected in 6.43s   EXIT=1
```

## 3. 会话级数据隔离只断行数，漏掉"只 UPDATE 的错账"

**改动文件**：`testcases/mes/data_isolation.py`（整体重写为 167 行）、
`testcases/mes/conftest.py:81-87`、新增用例 `test_mes_business.py:403-433`。

**变异方式**：只对流水表的金额列做 `UPDATE`，行数一个不变 ——
`UPDATE stock_ledger SET balance_milli = balance_milli + 1 WHERE id = (SELECT MAX(id) FROM stock_ledger)`
（另外也用"写流水时 balance 多记 1"演练过一遍，等价）。

**为什么没被检出**：改前 `snapshot()` 只返回
`{"counts": 8 张表的行数, "stock_available_total": SUM(stock.available_milli)}` 两个指标。
`stock_ledger.balance_milli` 既不在行数里，也不在库存合计里 ⇒ 完全在视野之外。
而且这里还有一个**时序陷阱**：`data_factory.cleanup()` 会把用例自己造的流水行删掉
（流水没有删除接口，只能直连库回收），会话收尾取快照时流水表实测是 **0 行**
（`SUM(balance_milli) = 0`）—— 所以"给快照再加一列流水合计"是**没用**的，
在正确时序下永远是 `0 == 0`，照样假绿。

**现在靠什么检出**：
1. `snapshot()` 扩成 `{"counts", "totals"}`，`totals` 覆盖 5 个关键数值列
   （`stock` 的 available/reserved/issued、`stock_ledger` 的 qty_milli/balance_milli），
   见 `data_isolation.py:36-44`、`:60-72`、`:80-82`；`describe_diff` 会打印每个数值列的基线与现值（`:153-167`）。
2. 新增 `ledger_balance_chain_errors(db_path)`（`data_isolation.py:85-150`）：
   **逐条重放流水**，每条 `balance_milli` 必须等于上一条的余额加上本条的带符号数量
   （`ISSUE` 为负、`RECEIPT`/`REVERSE` 为正），且末笔余额必须等于 `stock.available_milli`。
   期初值不硬编码种子，而是用两处事实反推：`期初 = 当前可用量 − 全部流水的带符号净变化`，
   所以用例新建物料、造多少流水都自洽。
3. 该检查挂在**两个时点**，覆盖"行还在"和"会话收尾"：
   - 用例正文 `test_ledger_balance_chain_matches_stock`（`test_mes_business.py:403-433`）在领料后立刻验；
   - `factory` fixture 在 `cleanup()` **之前**验一次（`conftest.py:81-87`）——
     这是流水行还活着的最后一个时点，清理一跑就永远验不到了。

**变异后结果**：

```text
MUTATION=只 UPDATE 流水金额（行数不变）：
  FAILED testcases/mes/test_mes_business.py::TestLedgerConsistency::test_ledger_balance_chain_matches_stock
  1 failed, 29 passed, 76 deselected, 22 errors in 7.44s   EXIT=1

MUTATION=写流水时 balance 多记 1：
  FAILED testcases/mes/test_mes_business.py::TestLedgerConsistency::test_ledger_balance_chain_matches_stock
  1 failed, 29 passed, 76 deselected, 22 errors in 7.41s   EXIT=1
```

> 那 22 个 `ERROR` 是 `factory` fixture teardown 里的余额链断言在所有用到工厂的用例上触发
> （同一个变异被 22 条用例各自抓到一次），不是崩溃 —— 只有 1 条 `FAILED` 是正文断言。
> `-m mes` 总数 30 = 修复前的 29 条 + 新增 1 条流水余额链用例。

## 4. 幂等键释放用例是空转

**改动文件**：`testcases/mes/test_mes_business.py:144-204`。

**变异方式**：把服务端的释放逻辑整个禁用 ——
`mock_server/idempotency.py:126-138` 的
`if exc_type is not None and self._claimed and self.key is not None:`
改成 `if False and ...`，让失败请求占的坑永远不被删除。

**为什么没被检出**：改前 `:164` 那行是

```python
first = mes.create_work_order("PLANNER", **base, order_no=duplicate)
```

**没传 `idem_key`**。而 `apis/mes_api.py:184` 的签名是
`create_work_order(self, role, idem_key=None, **payload)` ——
`idem_key=None` 时它走的是**普通 POST**，请求头里根本没有 `Idempotency-Key`。
也就是说：那次"本该占住幂等键的失败请求"从来没有占过坑，
第二次用同一个键当然会成功。用例断言的其实是"不带幂等键的普通请求也能成功"，
与"失败是否释放键"毫无关系 —— 所以把释放逻辑删掉也照样绿。

**现在靠什么检出**：
1. 第一次失败请求改为**带上同一个键**发出（`:179`）：

   ```python
   first = mes.as_role("PLANNER").post_idem("/work-orders", key, json=dict(base, order_no=duplicate))
   mes.expect_error(first, 400, "ORDER_NO_DUPLICATE")
   ```

   它真的会把 `key` 占成 `IN_PROGRESS`，于是"改完数据用同一个键重试必须成功"（`:186-188`）
   就成了真断言：服务端不释放 ⇒ 第二次拿到 `409 IDEMPOTENCY_KEY_CONFLICT`。
2. 补**负向对照**（`:190-204`）：键被**成功**请求占用后没有被释放，
   同键同体重放必须命中幂等回放（`X-Idempotent-Replay: true`、返回同一张工单、
   库里不多出新工单）。两条合起来才说明语义完整 = **失败释放、成功留存**。

**变异后结果**：

```text
MUTATION=释放逻辑 if False：
  apis.mes_api.ApiError: 期望 HTTP 201，实际 409
  {"code":"IDEMPOTENCY_KEY_CONFLICT","message":"同一个 Idempotency-Key 被用于了不同的请求内容",
   "detail":{"idempotency_key":"idem-release-VTKBQ8","scope":"work_order:create"}}
  apis\mes_api.py:136
  FAILED testcases/mes/test_mes_business.py::TestIdempotency::test_idempotency_key_is_released_after_a_failed_request
  1 failed, 29 passed, 76 deselected, 1 error in 7.07s   EXIT=1
```

## 5. README 实测结果块与 `--collect-only` 自相矛盾

**改动文件**：`README.md:234-259`。

**问题（改前的 README）**：`README.md:234` 自己写明"`-m api` 选到 91 条"，而实测代码块里却是
`pytest -m api  62 passed, 14 deselected in 36.20s` —— 同一页自相矛盾；
`-m mes` 行的 `47 deselected` 也与 `--collect-only` 报告的 105 冲突
（deselected 应 = 全量 − 选中 = 105 − 29 = 76，而不是 47）。

**修法**：本机能实跑的（`-m mes` / `-m login` / `--collect-only`）一律换成真实输出；
**打公网 `jsonplaceholder` 的 `-m api` 本机没有跑**（沙箱无外网），
只给出 `--collect-only` 的选取条数并显式标注"本机未跑"，不编造耗时。
UI 行同理标注（需 Chrome 与本机公网）。

**核对结论**：`-m api` 的 91/62 之争，根因是它把"纯接口 33 条"与
"MES 用例也打了 api 标记"这两件事混了 —— 见 README 里已经写明的那句
"三个标记有重叠，这些数字不能相加"。

## 经过这套变异实验后，简历那句话站得住吗？

**站得住**，判据是"把对应实现改坏，用例会不会红"：

| 简历措辞 | 对应变异 | 修前 | 修后 |
| --- | --- | --- | --- |
| 乐观锁并发 | `race` 换成串行 for 循环 | 29 passed | **2 failed** |
| 幂等键回放与冲突 | 禁用失败释放逻辑 | 29 passed | **1 failed** |
| 并发领料不超卖 | 去掉库存守卫 / 降级事务隔离 | 29 passed / 靠 500 | **1~2 failed** |
| 金额精度（原有） | 写流水 `balance + 1` | 29 passed | **1 failed**（新增余额链） |

唯一需要留意的是措辞边界：`并发领料不超卖` 的"不超卖"在本实现里
由 `BEGIN IMMEDIATE` + 库存守卫**两层**共同保证，用例对两层分别有断言
（守卫被删时 `IntegrityError`/500 被检出；隔离降级时 500 被检出），
所以不需要收窄措辞，但如果被追问"到底是哪一层防住的"，答案是：
**两层都在防，去掉任何一层用例都会红**。

## 复现方法

```powershell
# 主仓库：常规回归
cd auto-test-demo
.venv\Scripts\python.exe -m pytest -m mes -q      # 30 passed, 76 deselected

# 变异实验（在副本里做，别动主仓库）
# 1) 复制项目到 _mut2（排除 .venv/.git/__pycache__/.pytest_cache），并用目录联接指回主 venv
# 2) 按上文"变异方式"改副本中的 mock_server/ 或 testcases/
# 3) .venv\Scripts\python.exe -m pytest -m mes -q     # 期望：红
```

上面每一段的"变异后结果"都是档子里从副本跑出来的原始输出片段（`pytest -m mes -q`，
EXIT=1 才算检出）；副本连同变异脚本用完即删，主仓库里只留修复，不留日志文件。

**注意**：`pytest -m mes -q` 之外的变异组合（例如同时改事务隔离与库存守卫）
不在本文结论范围内；每条结论只对应上表列出的那一个最小改动。
